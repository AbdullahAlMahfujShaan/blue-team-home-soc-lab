# Microsoft Sysmon Setup & Telemetry Validation (`BTL-WIN11`)

This document describes the installation, configuration, and validation of **Microsoft Sysmon (System Monitor)** on the Windows 11 endpoint `BTL-WIN11`.

Sysmon provides enhanced endpoint telemetry that extends the visibility available through standard Windows Event Logs.

---

# 1. Overview

Microsoft Sysmon is part of the Microsoft Sysinternals suite.

Once installed as a Windows system service, Sysmon monitors system activity and records detailed telemetry to the Windows Event Log.

In this lab, Sysmon is used to monitor activity including:

- Process creation
- Parent/child process relationships
- Command-line execution
- Network connections
- DNS queries
- File creation
- Process access
- DLL/image loading
- Process metadata
- File hashes

The telemetry generated by Sysmon forms a major part of the endpoint visibility used throughout the Blue Team Home SOC Lab.

# 3. Why Sysmon?

Native Windows logs provide valuable security information, particularly authentication and account activity.

For example:

```text
Windows Security Log

4624 → Successful Logon
4625 → Failed Logon
```

However, additional endpoint visibility is useful during security investigations.

Sysmon extends this visibility:

```text
Windows Activity
      │
      ▼
    Sysmon
      │
      ├── Process Creation
      ├── Network Connections
      ├── DNS Queries
      ├── Process Access
      ├── File Creation
      ├── Image Loading
      └── Other Endpoint Telemetry
```

This provides analysts with significantly more context when investigating suspicious endpoint behaviour.

---

# 4. ARM64 Consideration

`BTL-WIN11` runs Windows 11 ARM64 because the host system uses Apple Silicon.

The ARM64 Sysmon executable was therefore used:

```text
Sysmon64a.exe
```

This differs from the traditional x64 executable commonly seen on Intel/AMD Windows systems.

# 17. Process GUID

One particularly useful Sysmon field is:

```text
ProcessGuid
```

Example:

```text
{XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX}
```

A Process GUID uniquely identifies a process instance.

This is useful because Windows Process IDs can eventually be reused.

The Process GUID can therefore help analysts correlate multiple events associated with the same process.

Example:

```text
Process Creation
      │
      │ ProcessGuid
      ▼
Network Connection
      │
      │ Same ProcessGuid
      ▼
DNS Activity
```

---

# 18. Parent/Child Process Relationships

Sysmon Event ID 1 also records parent process information.

For example:

```text
powershell.exe
      │
      └── whoami.exe
```

The `whoami.exe` event may contain:

```text
Image:
C:\Windows\System32\whoami.exe

ParentImage:
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
```

Parent/child relationships are extremely important during endpoint investigations.

---

# 19. Why Parent Processes Matter

Consider:

```text
explorer.exe
    │
    ▼
chrome.exe
```

This may be completely normal.

However:

```text
winword.exe
    │
    ▼
powershell.exe
```

may deserve additional investigation depending on context.

Similarly:

```text
powershell.exe
    │
    ▼
cmd.exe
    │
    ▼
whoami.exe
```

provides information about how commands were executed.

The process tree often provides more context than analysing a process name by itself.

# 27. Why DNS Telemetry Matters

DNS is frequently useful during security investigations because applications and malware often resolve domain names before making network connections.

An investigation might follow:

```text
Suspicious Process
        │
        ▼
DNS Query
        │
        ▼
Suspicious Domain
        │
        ▼
Resolved IP
        │
        ▼
Network Connection
```

Correlating process, DNS, and network telemetry can provide a much clearer picture of endpoint behaviour.

# 30. Event ID 7 — Image Loaded

```text
Event ID 7
```

records when a module such as a DLL is loaded into a process.

This can help investigate:

- Suspicious DLL loading
- DLL side-loading
- Unusual modules
- Process behaviour

Because image-load telemetry can be very noisy, effective Sysmon configuration and filtering are important.

---

# 31. Event ID 10 — Process Access

```text
Event ID 10
```

records when one process opens another process.

Conceptually:

```text
Source Process
      │
      │ accesses
      ▼
Target Process
```

This telemetry can be relevant when investigating techniques involving:

- Process injection
- Credential access
- Memory access
- Inter-process activity

However, legitimate applications also access other processes.

Therefore:

> Process Access telemetry is not automatically malicious.

Context must be investigated.

# 41. Security Considerations

Sysmon is a telemetry source.

It does not automatically mean that activity is malicious.

For example:

```text
whoami.exe
```

may appear during:

- Normal administration
- Troubleshooting
- Scripts
- Legitimate IT activity
- Attacker reconnaissance

Therefore:

```text
Process Name
     ≠
Verdict
```

An analyst must consider:

```text
Process
+
Command Line
+
Parent Process
+
User
+
Network Activity
+
DNS Activity
+
File Activity
+
Timeline
+
Environment Context
```

---

# 42. Telemetry vs Detection

Sysmon generates:

```text
Telemetry
```

It does not independently determine that every event is malicious.

For example:

```text
whoami
   │
   ▼
whoami.exe
   │
   ▼
Sysmon Event ID 1
```

This means:

```text
Process execution was observed.
```

It does **not** mean:

```text
An attack occurred.
```

Detection logic is applied later by tools such as Wazuh.
