# Investigation 001 — OneDrive Accessing Windows Explorer

## Investigation Summary

| Field | Value |
|---|---|
| Investigation ID | `INV-001` |
| Endpoint | `BTL-WIN11` |
| Data Source | Microsoft Sysmon |
| SIEM | Wazuh |
| Wazuh Rule ID | `92910` |

# 1. Executive Summary

Wazuh generated a **Level 12 alert** on the Windows 11 endpoint `BTL-WIN11` after Microsoft OneDrive accessed the Windows Explorer process.

The detection was generated by:

```text
Wazuh Rule 92910
```

with the description:

```text
Explorer process was accessed by
C:\Users\labadmin\AppData\Local\Microsoft\OneDrive\OneDrive.exe,
possible process injection
```

The underlying telemetry was:

```text
Sysmon Event ID 10 — Process Access
```

Because process access can be associated with techniques such as process injection and credential access, the alert required investigation.

Analysis of the source process, target process, user context, requested access rights, loaded Microsoft OneDrive components, call trace, and surrounding telemetry did not reveal additional evidence of malicious activity.

The source process was the legitimate Microsoft OneDrive client operating from the logged-in user's profile, and the call trace contained expected OneDrive synchronization components.

The alert was therefore classified as:

> **Likely Benign / Benign Positive**

This investigation demonstrates an important SOC principle:

> **A high-severity alert is not the same as a confirmed security incident.**

---

# 2. Investigation Objective

The objective was to determine whether:

```text
OneDrive.exe
      │
      │ Process Access
      ▼
Explorer.EXE
```

represented:

1. Legitimate OneDrive/Windows interaction,
2. Suspicious activity requiring further investigation, or
3. Malicious process injection requiring escalation.

# 5. Underlying Sysmon Event

The underlying Windows telemetry was:

```text
Sysmon Event ID 10
```

Event ID 10 represents:

```text
Process Access
```

Conceptually:

```text
Source Process
      │
      │ requests access to
      ▼
Target Process
```

In this investigation:

```text
OneDrive.exe
      │
      │ accesses
      ▼
Explorer.EXE
```

---

# 6. Source Process

The source process was:

```text
C:\Users\labadmin\AppData\Local\Microsoft\OneDrive\OneDrive.exe
```

This corresponds to the Microsoft OneDrive synchronization client installed under the user's profile.

The path was therefore consistent with expected OneDrive installation behaviour.

However:

> A legitimate-looking filename or path alone is not sufficient to classify a process as benign.

Additional context was required.

---

# 7. Target Process

The target process was:

```text
C:\WINDOWS\Explorer.EXE
```

Windows Explorer is the standard Windows graphical shell and file-management process.

Because OneDrive integrates with Windows Explorer to provide synchronization status and file-system integration, interaction between these two processes can be legitimate.

Nevertheless, process-access telemetry was investigated because similar behaviour can also occur during malicious process injection.

---

# 8. Source and Target Relationship

The observed relationship was:

```text
Microsoft OneDrive
        │
        │ Process Access
        ▼
Windows Explorer
```

This relationship is more plausible as legitimate activity than an unknown executable accessing Explorer.

For comparison:

```text
C:\Users\Public\update.exe
        │
        │ Process Access
        ▼
Explorer.EXE
```

would require significantly more scrutiny.

Process names must therefore always be evaluated together with:

- File path
- User
- Process relationship
- Access rights
- Call trace
- Timeline
- Surrounding events

---

# 9. User Context

The source user was:

```text
BTL-WIN11\labadmin
```

The target user was also:

```text
BTL-WIN11\labadmin
```

Therefore:

```text
SourceUser == TargetUser
```

The process interaction occurred within the same logged-in user context.

This was consistent with normal desktop OneDrive integration.

---

# 10. Granted Access

The Sysmon event recorded:

```text
GrantedAccess:
0x101411
```

The presence of process-access rights is what caused the event to be security-relevant.

However:

```text
Process Access
      ≠
Process Injection
```

Legitimate Windows applications frequently request handles to other processes.

The access value therefore had to be interpreted together with the source process and call trace rather than treated as proof of compromise.

---

# 11. Call Trace Analysis

One of the most useful fields in the event was:

```text
CallTrace
```

The observed trace included:

```text
C:\WINDOWS\SYSTEM32\ntdll.dll+1284
```

followed by Microsoft OneDrive components including:

```text
C:\Users\labadmin\AppData\Local\Microsoft\OneDrive\
26.158.0816.0003\FileSyncClient.dll+6a0b80
```

Additional OneDrive components included:

```text
FileSyncClient.dll
FileSyncEvents.dll
FileSyncHost.DLL
```

The trace also contained standard Windows runtime components:

```text
C:\WINDOWS\System32\ucrtbase.dll
C:\WINDOWS\System32\KERNEL32.DLL
C:\WINDOWS\SYSTEM32\ntdll.dll
```

---

# 12. Why the Call Trace Was Important

The call trace helped answer:

```text
Which code was responsible for accessing Explorer?
```

Instead of showing an unknown or obviously suspicious module, the trace contained components associated with:

```text
Microsoft OneDrive
+
Windows system libraries
```

This increased confidence that the process access was associated with legitimate OneDrive functionality.

---

# 14. Initial Hypotheses

Three primary hypotheses were considered.

## Hypothesis 1 — Legitimate OneDrive Activity

```text
OneDrive
    │
    ▼
Explorer Integration
    │
    ▼
Expected Process Access
```

This was plausible because OneDrive integrates directly with Windows Explorer.

---

## Hypothesis 2 — Compromised OneDrive Process

A legitimate process could theoretically be abused or compromised.

For example:

```text
Attacker
   │
   ▼
Compromised OneDrive.exe
   │
   ▼
Explorer.EXE
```

This required checking whether surrounding evidence suggested abnormal behaviour.

---

## Hypothesis 3 — Process Injection

The detection specifically warned about possible process injection.

Conceptually:

```text
Source Process
      │
      ▼
Access Target Process
      │
      ▼
Manipulate Target Memory
      │
      ▼
Execute Code
```

The investigation therefore searched for evidence supporting this scenario.

---

# 15. Surrounding Telemetry

The alert was reviewed together with nearby Wazuh events.

The surrounding documents primarily showed the same process-access alert and did not reveal an obvious cluster of additional suspicious activity.

No immediate evidence was identified indicating:

- Unknown executable execution
- Suspicious PowerShell activity associated with this event
- Unexpected child processes
- Obvious malicious network activity
- Additional correlated injection behaviour
- Unexpected user context

This reduced the likelihood that the event represented an active compromise.

---


Consistent with the user's OneDrive installation.

### Target

```text
C:\WINDOWS\Explorer.EXE
```

A logical target for OneDrive shell integration.

### User Context

```text
BTL-WIN11\labadmin
```

for both source and target.

### Call Trace

```text

FileSyncEvents.dll
FileSyncHost.DLL
```

### Surrounding Activity

No obvious correlated malicious event cluster was identified during the investigation.

---

# 17. Evidence That Would Have Increased Suspicion

The verdict would have changed if evidence such as the following had been observed:

```text
OneDrive.exe running from an unusual directory
```

For example:

```text
C:\Users\Public\OneDrive.exe
C:\Temp\OneDrive.exe
```

Other suspicious indicators would include:

- Unexpected process owner
- Unknown DLLs in the call trace
- Suspicious child processes
- Encoded PowerShell execution
- Unexpected outbound connections
- Persistence mechanisms
- Credential-access activity
- Multiple unrelated process-access events
- Suspicious file creation
- Known malicious hashes
- Unusual parent process relationships

# 20. Analyst Conclusion

The Wazuh detection correctly identified security-relevant behaviour:

```text
One process accessed another process.
```

This type of behaviour can be associated with process injection.

However, investigation showed that the source process was Microsoft OneDrive and the target was Windows Explorer.

The call trace contained expected OneDrive synchronization components and standard Windows libraries.

No additional correlated evidence of malicious behaviour was identified during the investigation.

The alert was therefore assessed as legitimate application behaviour that happened to match detection logic designed to identify potentially dangerous process-access patterns.

# 29. Lessons Learned

## Lesson 1 — Never Judge an Alert by Severity Alone

```text
Level 12
```

does not automatically mean:

```text
Critical Incident
```

---

## Lesson 2 — Process Access Is Context Dependent

```text
Process A
   │
   ▼
Process B
```

can occur during both:

```text
Normal Software Behaviour
```

and:

```text
Malicious Process Injection
```

---

## Lesson 3 — Call Traces Are Valuable

The call trace helped connect the activity to:

```text
FileSyncClient.dll
FileSyncEvents.dll
FileSyncHost.DLL
```

which provided additional context supporting legitimate OneDrive behaviour.

---

## Lesson 4 — File Paths Matter

Compare:

```text
C:\Users\labadmin\AppData\Local\Microsoft\OneDrive\OneDrive.exe
```

with:

```text
C:\Temp\OneDrive.exe
```

The filename may be identical.

The context is not.

---

# 30. What I Would Do in a Production Environment

A production investigation could go further by validating:

- Executable digital signature
- File hash
- File reputation
- OneDrive version
- Process ancestry
- Full endpoint timeline
- Related DNS queries
- Related network connections
- File creation activity
- Other Event ID 10 activity
- Endpoint Detection and Response telemetry
- Threat intelligence
- Historical prevalence across endpoints

For example, a hash could be calculated using:

```powershell
Get-FileHash `
"C:\Users\labadmin\AppData\Local\Microsoft\OneDrive\OneDrive.exe" `
-Algorithm SHA256
```

The hash could then be compared with approved software inventories or appropriate threat-intelligence sources.

These additional validation steps were not required to reach the lab verdict but would strengthen a production investigation.

---

# 31. Potential Detection Tuning

If the same known-good OneDrive behaviour repeatedly generates identical alerts across trusted endpoints, detection tuning could eventually be considered.

However:

> Do not immediately suppress an alert simply because one occurrence was benign.

Before tuning, determine whether:

- Behaviour is consistently identical
- Executable path is stable
- Digital signature is valid
- User context is expected
- Access pattern is understood
- Suppression would create a detection blind spot

A safer tuning strategy would use multiple conditions rather than simply excluding:

```text
OneDrive.exe
```

by filename.

# 35. Key Takeaway

The most important lesson from this investigation is:

> **An alert is evidence to investigate, not a verdict.**

Wazuh correctly identified behaviour associated with a potentially dangerous technique.

The analyst's responsibility was to determine whether the behaviour was actually malicious.

In this case:

```text
High-Severity Detection
        │
        ▼
Investigation
        │
        ▼
Context
        │
        ▼
Evidence
        │
        ▼
Likely Benign
```

That distinction is fundamental to effective SOC analysis.
